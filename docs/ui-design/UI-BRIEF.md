## 1. 一页纸产品背景（设计师必读）

**teamem 是什么**：开源、可自托管的**团队知识编译服务**。它从 GitHub（commit/PR/
issue/评论）、命令行工具（`teamem init` 扫描存量代码）、AI agent（MCP 写入）三个
入口摄取团队的开发事件，用 LLM 把这些原始事件**编译**成结构化的「概念页」——
带证据、带贡献者、带时间线的团队知识。开发者的 AI coding agent（Claude Code 等）
通过 MCP 直接检索这些知识；人类通过本次要设计的 Web UI 浏览和管理。

**核心卖点（UI 要讲的故事）**："为什么"时刻——新人问「为什么 X 用了 Y 方案」，
得到一个决策页：结论 + 当时的 PR 讨论链接 + 落地的 commit。知识不是靠人写文档，
是从真实开发活动里编译出来的，**每一条都有可点击回溯的证据**。

**Web UI 的定位**：不是产品的主要消费界面（agent 走 MCP 才是），而是：
1. **首次部署引导**——让一个陌生人 30 分钟内从 `docker compose up` 走到
   「agent 问出第一个带引用的回答」，全程零终端操作（这是 M2 的核心验收）；
2. **知识库的人类浏览面**——浏览、检索、看证据；
3. **团队管理面**——成员/角色、API key、摄取源、LLM 配置、审计、清除。

**用户画像**：
- **部署者/Owner**——技术 lead，自己起 Docker，最在意「快点接好、看到第一页知识」；
- **团队成员**——日常写代码的开发者，主要在 agent 里用，偶尔来 UI 查证据、看全文；
- **管理员**——管 key、管成员、看审计；小团队里往往和 Owner 是同一人；
- **评估者（design partner）**——正在决定要不要采用的外部团队，第一印象极重要。

**技术约束**：shadcn/ui + Tailwind + Vite SPA（React），由 server 直接托管，
无 SSR。桌面优先（开发者工具）。组件尽量落在 shadcn 现有组件族上。

## 2. 角色权限矩阵（决定每个按钮对谁可见/禁用）

四个角色，能力**递增叠加**（member 拥有 viewer 的一切，以此类推）：

| 能力 | viewer | member | admin | owner |
|---|---|---|---|---|
| 浏览概念页列表/详情、任务(job)列表 | ✅ | ✅ | ✅ | ✅ |
| 语义检索、上下文预览、事件 payload 详情 | ❌ | ✅ | ✅ | ✅ |
| API key 管理（铸造/吊销）、摄取源配置、LLM 配置、审计查询 | ❌ | ❌ | ✅ | ✅ |
| 项目清除（purge）、成员角色管理、删除团队 | ❌ | ❌ | ❌ | ✅ |

设计要求：
- 无权限的操作**优先隐藏**而不是禁用；确需展示的（如配置页对 viewer），用
  只读态 + 说明「需要 admin 权限」；
- M2 验收里有一条专门测这个：邀请一个 viewer，验证其改配置被拒——所以
  viewer 的只读态不是边角料，是被验收的行为。

> ⚠️ 开放问题（见 §10）：契约原文对 viewer 能否看「事件 payload 详情」是清楚的
> （不能），但概念页详情 viewer 应当可看（浏览的应有之义）。以上矩阵按此理解绘制，
> 拍板见 §10-Q1。

## 3. 信息架构总览

```text
未登录
├── 登录页（Sign in with GitHub）
└── 邀请接受页（/invite/<token>）

已登录（全局框架：左侧导航 + 顶部栏）
│
│  顶部栏：团队切换器 ▾ · 项目切换器 ▾ ·（右侧）搜索入口 · 用户菜单（头像 ▾）
│
├── 首次引导向导（首个用户/新团队自动进入，5 步）
│
├── 知识库                     ← 登录后的默认落地页
│   ├── 概念页列表（筛选/检索）
│   ├── 概念页详情（正文/证据/贡献者/时间线）
│   └── 上下文预览（SessionStart 注入内容预览）
│
├── 活动
│   ├── 事件列表（摄取活动）
│   │   └── 事件详情（payload，member+，读取被审计）
│   └── 编译任务列表
│       └── 任务详情（逐事件结果）
│
├── 成员
│   ├── 成员与角色列表（邀请/改角色/移除）
│   └── 成员资料页（贡献过的概念页）
│
├── 设置
│   ├── API keys（铸造/吊销/轮换）
│   ├── 摄取源（GitHub App / CLI / MCP 接入状态与指引）
│   ├── LLM 与检索（provider 四家、语义能力状态、编译节奏）
│   ├── 项目设置（含危险区：purge）
│   └── 团队设置（含危险区：删除团队）
│
├── 审计（admin+）
│
└── 占位（P2，"讲故事"）：矛盾对账 · 失效检测 · 团队简报
```

导航模型要点：
- **团队 → 项目**两级作用域。几乎所有页面都在「当前项目」作用域内；成员、
  团队设置、部分 key 属团队作用域。切换器要清楚表达「我现在看的是哪个团队
  的哪个项目」；
- 多团队是 M2 真实能力：一个用户可属于多个团队，团队间数据完全隔离。

## 4. 逐页详单

格式：**目的 → 页面内容 → 操作（按钮/表单）→ 状态 → 优先级**。
「数据字段」全部来自冻结契约，是真实存在的，设计师可放心使用。

### A. 认证与进入

#### A1. 登录页 —— P0

- **目的**：唯一的身份入口。没有账号密码——身份就是 GitHub。
- **内容**：产品名/logo、一句话定位、一个主按钮。
- **操作**：`Sign in with GitHub`（唯一主操作）。
- **状态**：
  - OAuth 失败/取消 → 错误提示，可重试；
  - **未受邀用户登录**：能通过 OAuth，但不属于任何团队 → 引导页
    「你还不在任何团队里——请向管理员索取邀请链接」（不能是裸报错）；
  - **系统首个用户**：登录后自动成为 team owner，直接进入首次引导向导；
  - **服务器未配置 GitHub App**：`Sign in with GitHub` 按钮直接不可用/隐藏，
    显示「部署者需要先在 GitHub 上创建一个 GitHub App 并写入 `.env`，见
    README」——不能让按钮点了没反应或跳一个 GitHub 404。
- **⚠️ 这一步不是「零前置配置」**：登录用的是 operator 部署前在 GitHub 上
  创建的那个 GitHub App（见上方 2026-07-29 决定），意味着**在第一次
  `docker compose up` 之前**，operator 已经需要去 GitHub 建好 App、把
  App ID / Client ID / Client Secret / Private Key 填进 `.env`。这件事
  不发生在浏览器里，M2 的「30 分钟零终端」验收指的是**建完 App 之后**
  浏览器里的部分——README 的部署前置步骤必须把这一步讲清楚，A1 页面本身
  不需要（也不能）替 operator 做这件事。
- 设计注意：这是评估者看到的第一个页面，值得放一句核心卖点。

#### A2. 邀请接受页 —— P0

- **目的**：受邀成员通过邀请链接加入团队。
- **内容**：邀请者/团队名、将获得的角色、`Sign in with GitHub to join` 按钮。
- **状态**：链接已过期/已用 → 明确失效态；已登录用户点击 → 跳过 OAuth 直接确认加入。

### B. 首次引导向导（Onboarding Wizard）—— P0，M2 的灵魂

> M2 核心验收：陌生人只凭 README，从 `docker compose up` 到「agent 问出第一个
> 带引用的回答」≤30 分钟、零求助、**全程不进容器敲命令**。这个向导承担其中
> 浏览器侧的全部工作。设计目标：每一步都「下一步该干嘛」毫无歧义。

五步，带进度指示，可中途退出、回来续做（向导记住进度）：

**Step 1 · 建团队与项目**
- 表单：团队名、首个项目名（各一个文本框，给默认值建议）。

**Step 2 · 配置 LLM provider**（编译能力的硬前提）
- 四选一：Anthropic / OpenAI / OpenRouter / 自定义 OpenAI 兼容端点
  （自定义 = base URL + key 两个字段，必须同时填）；
- key 输入框（密文显示）+「测试连接」按钮 → 成功/失败即时反馈；
- **语义检索能力提示**：配好后显示两种能力状态之一——
  `✓ 语义检索可用（vector）` 或 `⚠ 该 provider 无 embedding 能力，检索将降级
  为关键词模式（FTS）`——这是产品红线「降级必须明示」的 UI 落点，Anthropic
  单独配置时真实会发生；
- 允许「暂时跳过」，但要写明后果：跳过则编译不会运行，知识库保持为空。

**Step 3 · 确认摄取范围（复用登录时的同一个 GitHub App）**
- **不是第一次连接**——owner 在 A1 登录时已经用这个 GitHub App 完成了 OAuth
  授权；这一步做的是**安装/确认**这个 App 在哪些仓库上生效（GitHub App 的
  "installation"是独立于 OAuth 授权的另一个动作，登录不会自动装到任何仓库上，
  这一步不能省）；
- 「在 GitHub 上管理仓库访问范围」跳转按钮 → 回来显示已授权的仓库列表；
- webhook secret 状态（自动生成，不需要用户手填）；
- 可跳过（用 CLI/MCP 也能供数据）。
- 文案要避免让用户以为在"重新登录 GitHub"——用"选择仓库"而不是"连接 GitHub"
  这类措辞，减少"我是不是已经做过这步了"的困惑。

**Step 4 · 铸第一把 API key + 接入命令**
- 自动铸一把绑定当前项目的 key；
- **明文只显示这一次**（大号可复制区域 + 醒目警告「离开本页后无法再次查看」）；
- 同屏给出三段可复制命令（这是后端已实现的真实能力，M1-MCP-06）：
  1. `claude mcp add ...`（把团队知识接进 Claude Code）；
  2. `teamem init --url ... --token ... --project ...`（扫描存量仓库冷启动）；
  3. SessionStart hook 安装命令（`teamem cli install-hook`，M2 新增）。
- 每段命令旁配一行「这条命令做什么」。

**Step 5 · 完成/等待第一页知识**
- 实时状态区：「已收到 N 个事件 · M 个编译任务运行中 · 已产出 K 个概念页」；
- 产出第一页时就地展示卡片 →「查看你的第一条团队知识」；
- 长时间无数据 → 诚实空态 + 排查指引（「还没收到事件？检查 …」）。

### C. 知识区（日常使用核心）

#### C1. 概念页列表 —— P0（登录后默认落地页）

- **目的**：浏览 + 检索团队知识库。
- **列表行字段**（真实契约字段）：
  - 标题；
  - **类型徽章**，六种：`decision` 决策 / `gotcha` 坑 / `convention` 约定 /
    `runbook` 操作手册 / `service` 服务 / `concept` 概念——需要六个可区分的
    视觉标识（色 + 图标），这套徽章会贯穿全产品；
  - **状态徽章**，四种：`active` / `superseded` 已被取代 / `disputed` 有矛盾 /
    `needs-review` 待复核（disputed 要有警示感）；
  - **置信度**，三档：high / medium / low（建议弱视觉，如三格小条）；
  - path（如 `backend/auth/jwt-rotation`，等宽字体）；
  - 贡献者头像组（最多 N 个 + 溢出计数）；
  - 证据数（如「3 条证据」）；
  - last_confirmed 相对时间（「上次确认于 …」——注意语义是**被证据再次确认**
    的时间，不是普通编辑时间，文案不要写成 updated）。
- **操作**：
  - **检索框**（member+）：语义混合检索，输入自然语言（支持中文、换说法命中）；
    检索结果带相关度；**降级横幅**：语义不可用时显示
    「⚠ 当前为关键词检索模式（语义检索未启用）」——红线要求，必须设计；
  - 筛选器：类型（6 多选）、状态（4 多选）、置信度、标签、贡献者；
  - 排序固定 last_confirmed 倒序；
  - 分页：**游标式**——只有「加载更多/下一页」，没有页码跳转（契约如此）。
- **检索结果行的三条真实约束**（来自 M1 验收库实测，见
  [UI-SAMPLES §3.5](./UI-SAMPLES.md)——不遵守会做错）：
  1. **relevance 不是百分比匹配度**。它是余弦相似度，一次完全正确的命中
     真实值也可能只有 **0.36**；渲染成「36% 匹配」会让用户误以为结果很差。
     **不要显示原始数值**，只用于排序，或用高/中/低三档表达；
  2. **结果行不含正文或摘要片段**——契约（N7）规定列表只返回摘要字段
     （title + tags + 元数据）。不要设计成「每条结果下有两行正文预览」的样子，
     后端给不了这个数据；
  3. **两个降级标记是独立的**：`degraded`（整次检索降级）驱动上面那条
     降级横幅；`ftsFallback`（单行来自关键词兜底）用于单行的弱标记。
- **状态**：空库（新团队）→ 诚实空态 + 三条接入路径的 CTA（连 GitHub /
  跑 teamem init / 接 MCP）；检索无结果；加载骨架。
- viewer 可浏览列表但**无检索框**（检索是 member+ 能力）→ 需要设计 viewer
  视角的该页变体。

#### C2. 概念页详情 —— P0（整个产品价值的落点）

- **目的**：完整呈现一条知识及其可信度来源。「为什么」时刻的最终画面。
- **内容分区**：
  1. **头部**：标题、类型徽章、状态徽章、置信度、当前 path（可复制）、
     历史别名（收起态）、last_confirmed、created；
  2. **正文**：Markdown 渲染；正文内的 `teamem://concept/<uuid>` 内链渲染为
     应用内跳转链接（知识之间互相引用是一等能力）；
  3. **证据（Evidence）**——本页最重要的区块，每条证据：
     - 类型（commit / PR / issue / PR 评论 / repo 文件）+ 对应图标；
     - 不可变外链：GitHub permalink（commit SHA、PR 链接、评论 permalink，
       repo 文件证据 = 仓库+commit SHA+路径）；
     - 发生时间；
     - 设计要传达「这条知识是有出处的，点一下就能回到现场」；
  4. **贡献者**：头像 + 名字，**已绑定 web 账号的**点击进成员资料页（M2 验收
     点名要求「贡献者链接指向真实成员资料，不是占位符」）；未绑定的纯 GitHub
     贡献者显示 GitHub 头像/login，跳其 GitHub 主页（处理方式见 §10-Q6）；
     **还有第三种：`service` 主体**（服务账号，无头像无主页可链）——真实数据里
     它是多数，见 §10-Q9 与 [UI-SAMPLES §2.4](./UI-SAMPLES.md)；
     **注意贡献者为空是默认态**（真实 48 页里只有 5 页有贡献者，因为
     `client_claimed` 不进贡献者），空态必须设计；
  5. **时间线**：该概念关联事件按 occurred_at 排列（后端 timeline 能力已存在）；
  6. `disputed` 状态的页面：顶部矛盾警示条 +（P2 占位）「查看矛盾对账」入口。
- **操作**：复制 path / 复制 UUID / 复制页面链接；（P2 占位：人工确认、
  标记过期、编辑——M2 无人工编辑能力，不要设计成可编辑的样子）。
- **状态**：404（重要红线：**跨团队访问和真不存在返回完全同一个 404**，
  所以 404 页只能设计一种，文案不得暗示「存在但无权」）。

#### C3. 上下文预览 —— P0

- **目的**：预览 SessionStart 自动注入端点（`GET /v1/context`）会给 agent 塞
  什么——「你的 agent 每次开新会话会自动知道这些」。
- **内容**：渲染后的 markdown 摘要（近期 N 个高置信度概念页：标题 + 一行摘要 +
  链接）；**token 预算指示**（如「~450 tokens / 预算 800」）；空库时的空态。
- **操作**：刷新预览；复制 hook 安装命令（引导没装 hook 的用户去装）。
- member+ 可见。

### D. 活动区（摄取与编译的可观测性）

#### D1. 事件列表 —— P1

- **目的**：回答「我的数据进来了吗」——尤其是引导期和排障时。
- **列表行**：来源徽章（GitHub push/PR/issue/评论 · CLI init · MCP write，
  各配图标）、actor（头像+名，**多数为空**——契约允许 actor 未知，显示
  「未知」而不是编造一个系统头像）、actor 可信度标记（`webhook_verified` ✓ /
  `client_claimed` 无标）、occurred_at、摘要一行。
- ⚠️ **真实比例**：验收数据 82 条事件里 **78 条 actor 为空**（CLI 扫描与 MCP
  写入天然无可验证 actor），只有 4 条 GitHub 事件有 actor 且带 ✓。
  **不要把"有头像的行"设计成默认态**——见 [UI-SAMPLES §5.1](./UI-SAMPLES.md)。
  GitHub actor 对象含 `providerUserId`（GitHub 数字 ID），头像可直接用
  `avatars.githubusercontent.com/u/<id>` 取，无需额外 API。
- **操作**：按来源筛选；游标分页；点击进详情（member+）。
- viewer 视角：可见列表、不可进 payload 详情。

#### D2. 事件详情 —— P1

- **内容**：事件元信息 + **脱敏后的 payload**（JSON 查看器）。
- **两个必须设计的特殊态**：
  1. 进入 payload 区前或同时提示「payload 读取会被记入审计日志」（读 payload
     是被审计的敏感操作）；
  2. **审计写入失败 → 读取被拒**（红线 fail-closed）：设计一个「暂时无法读取
     （审计服务不可用）」的错误态——这不是普通报错，是产品原则。

#### D3. 编译任务列表 —— P1

- **列表行**：任务 kind、**状态徽章**（`queued` → `processing` →
  `completed` / `failed` / `cancelled`，五态）、事件数、发起者、created、耗时。
- **操作**：按状态筛选；游标分页。

#### D4. 任务详情 —— P1

- **内容**：任务元信息 + **逐事件结果列表**，每行四种结局之一：
  - `compiled` → 链到产出的概念页；
  - `skipped` + 原因（枚举，**真实取值只有 `no_knowledge` 与
    `already_compiled` 两个**，拿不到模型的具体理由）；
  - `failed` + **脱敏后的错误**（永远不含原始 payload/prompt/密钥）；
  - **`pending`** —— 任务已建、该事件尚未处理。此前本清单漏了这一态，
    但它是契约 `jobEventResult` 的四个分支之一，真实数据里有 9 条。
- **真实比例**（见 [UI-SAMPLES §5.5](./UI-SAMPLES.md)）：compiled 61 /
  skipped 10 / pending 9。**skipped 占 12%，不是罕见态**，它的样式要认真设计
  （中性灰，不是错误色）。真实错误只有一条 `no_llm_provider`，message 本身
  就是可执行的排查指引——错误组件应把它当正文渲染，不要折叠成一行小字。
- 失败态是排障入口，信息层级要清楚。

### E. 成员区

#### E1. 成员与角色 —— P0

- **列表行**：GitHub 头像、login、显示名、**角色**（owner/admin/member/viewer
  徽章）、加入时间。
- **操作**：
  - `邀请成员` → 弹窗：选角色 → 生成邀请链接（可复制、显示有效期）；
  - 角色下拉修改（owner 才能操作；不能把自己降级到失去唯一 owner）；
  - 移除成员（确认弹窗）。
- **状态**：只有自己一人时的空态（CTA：邀请第一个同事）。

#### E2. 成员资料页 —— P1

- **内容**：头像、GitHub login（外链）、角色、加入时间、**贡献过的概念页列表**
  （复用 C1 行组件）。
- 这是 C2 贡献者链接的落点，M2 验收会点开检查。

### F. 设置区（admin+，除项目基本信息外）

#### F1. API keys —— P0

- **列表行**：key 名/标签、key ID 前缀（`key_...`，**这不是密钥本身**，可明文
  显示）、绑定范围（某项目 / `所有项目`——团队级 key 是显式选项）、scope 标签
  （`read` / `read:payload` / `write` 等数据面 scope）、创建时间、状态
  （active / 已吊销）。
- **操作**：
  - `铸造新 key` → 弹窗：名称、绑定项目（或勾选 allProjects）、scope 多选 →
    成功页 = **明文一次性展示**（同引导 Step 4 的组件：大字号、复制按钮、
    「离开后不可再查看」警告、附 `claude mcp add` 可粘贴命令）；
  - `吊销`（确认弹窗，文案明确「立即生效，使用该 key 的请求马上 401」）；
  - `轮换`（= 铸新 + 吊销旧，警告旧 key 立即失效——M1 实测中曾因此把正在用的
    key 弄失效，警告不能省）。
- **状态**：已吊销行置灰；空态。

#### F2. 摄取源 —— P0

三个来源各一块卡片：

1. **GitHub App**：连接状态、App/installation 信息、覆盖仓库列表、webhook
   secret 状态（可重新生成）、最近投递状态（最近 N 次 webhook 成功/失败）；
   未安装到任何仓库 → 引导按钮（**这是同一个用于登录的 GitHub App**，这里
   管理的是它的 installation 范围，不是重新建一个连接——文案与引导 Step 3
   一致）；
2. **CLI（teamem init）**：不是"连接"，是指引卡——展示带当前项目参数的完整
   命令（联动 F1 选一把 key）、最近一次 init 摄取的时间/规模；
3. **MCP**：指引卡——`claude mcp add` 命令展示 + 复制；已接入的提示。

#### F3. LLM 与检索 —— P0

- **provider 配置**：同引导 Step 2 的完整版（四家、测试连接、更换 key）；
- **语义能力状态**：明示当前 `vector` 或 `fts-only` 模式，fts-only 时解释
  原因与影响（检索降级、跨语言合并不可用）——**常驻状态而非一次性提示**；
- **编译节奏**：预留一块设置（选项待产品定，见 §10-Q5）。

#### F4. 项目设置 —— P0

- 项目名、项目 ID（可复制）；
- **危险区**：`清除项目数据（Purge）`（owner）——确认弹窗要求输入项目名；
  执行后成功页显示**删除计数**（删了多少事件/概念页/任务——契约要求记录删除
  数量），并明示「审计记录与成员身份已保留」。

#### F5. 团队设置 —— P0

- 团队名；新建团队入口（多团队真实能力）；
- **危险区**：删除团队（owner，双重确认）。

#### F6. 审计日志 —— P0（admin+）

- **目的**：M2 验收原文「审计页可查『谁在什么时候读了哪条知识』，支持按
  actor/时间筛选」。
- **列表行**：时间、actor（头像+名）、动作类型、资源（类型 + ID，链到资源页）、
  request ID。**没有任何内容列**——契约规定审计不存 payload、不存检索原文，
  设计时不要留「详情展开看内容」的交互暗示；
- **操作**：按 actor 筛选、时间范围、动作类型、项目；游标分页；
- purge 操作在这里留痕（M2 验收点）。

## 5. 全局组件与通用状态（跨页面复用，一次设计到位）

1. **六类型徽章 + 四状态徽章 + 三档置信度**——全产品最高频视觉词汇，优先定稿；
2. **诚实空态**（工程红线：无数据必须显示诚实空态，禁止假数据填充）——每个
   列表页都要有：插画/图标 + 一句话 + 指向解决路径的 CTA；
3. **降级横幅**（fts-only 模式）——检索框附近 + 设置页常驻状态两种形态；
4. **一次性明文展示组件**（key 铸造）——引导 Step 4 与 F1 复用；
5. **可复制命令块**——带语法高亮、复制按钮、一行用途说明；引导、F1、F2 多处复用；
6. **证据条目组件**——C2、时间线、（未来）审计跳转复用；
7. **统一 404**——一种设计，文案中性（「没有找到该资源」），不区分无权/不存在；
8. **权限拒绝态**——viewer 触到 member+ 功能时的引导（「需要更高权限，联系管理员」）；
9. **审计提示条**——payload 读取处；
10. **加载骨架**——列表与详情两套；
11. **危险操作确认弹窗**——purge/删团队（输入名称确认）与吊销 key（普通确认）两档；
12. **团队/项目切换器**——含新建入口；
13. **相对时间与语义区分**——`last_confirmed`（被证据确认）vs `created` vs
    `occurred_at`（事件发生于源头的时间），三个时间概念文案不能混。

## 6. 四条关键用户旅程（设计师用来自检流程完整性）

**J1 · 部署者的 30 分钟**（M2 头号验收）
（前置，不计入 30 分钟、也不在浏览器里：operator 已按 README 在 GitHub 上
建好一个 GitHub App，填进 `.env`）→ `docker compose up` →（浏览器）登录页 →
GitHub OAuth → 自动成为 owner → 引导 5 步（Step 3 只是确认仓库范围，
不是再连一次）→ 复制 `teamem init` 命令去终端跑 → 回到 Step 5 看到事件数
上涨 → 第一个概念页出现 → 点开看到证据。
*设计自检：每一步的「下一步做什么」是否无歧义？等待编译时用户看什么？*

**J2 · 受邀成员的第一天**
收到邀请链接 → OAuth → 落在知识库列表 → 检索一个自然语言问题 → 打开概念页 →
点证据 permalink 回到当年的 PR 讨论 → 复制 `claude mcp add` 把知识接进自己的
Claude Code。

**J3 · 日常「为什么」时刻**（产品核心故事）
成员在 UI 检索「为什么我们不用 X」→ 命中一条 `decision` 页 → 看到结论、当时的
PR 讨论链接、落地 commit、参与讨论的同事头像 → 点头像看这位同事还贡献了什么。

**J4 · 管理员的治理日**
铸一把只读 key 给 CI → 吊销一把泄露的 key（确认立即 401）→ 审计页查「上周谁
读过支付项目的 payload」→ purge 一个试验项目 → 确认审计留痕、删除计数正确。

## 7. 数据真实性速查表（设计 mock 内容时用真实枚举）

| 维度 | 合法值（冻结契约，不许自造） |
|---|---|
| 概念类型 | decision · gotcha · convention · runbook · service · concept |
| 概念状态 | active · superseded · disputed · needs-review |
| 置信度 | high · medium · low |
| 任务状态 | queued · processing · completed · failed · cancelled |
| 逐事件结果 | compiled · skipped · failed · **pending** |
| skip 原因（枚举） | `no_knowledge` · `already_compiled`（只有这两个） |
| 事件来源 | GitHub push/commit · PR · issue · PR/issue 评论 · cli_init · mcp_write |
| actor 可信度 | webhook_verified（打勾标）· client_claimed（不进贡献者） |
| 证据形态 | commit SHA · PR 链接 · issue 链接 · 评论 permalink · repo 文件(仓库+SHA+路径) |
| path 规则 | 全小写，`[a-z0-9-]` 段用 `/` 分隔，如 `backend/auth/jwt-rotation` |
| 分页 | 游标式，默认 20 条，上限 100 |
| 角色 | owner · admin · member · viewer |

Mock 文案建议用真实感的开发知识（如「决策：JWT 改用 RS256 轮换」「坑：pgvector
索引在 UPSERT 后需要 ANALYZE」），能同时当产品叙事素材。

> **更好的选择**：不用编——[UI-SAMPLES.md](./UI-SAMPLES.md) 提供了 M1 验收库
> 导出的 **48 个真实概念页**（含完整正文、真实 tags、真实证据、真实时间戳）
> 与活动区/审计区的真实数据密度。直接用那些内容，高保真稿就是产品实拍级别，
> 而且能避开几个"编 mock 数据编不出来"的真实形态（长正文、空贡献者、
> service 主体、relevance 只有 0.36 等）。

## 8. 必须遵守的产品原则（工程红线的 UI 翻译）

1. **不许假装**：任何未实现能力不得做成可点击的样子；占位必须明确标注「即将推出」；
2. **降级必须明示**：语义检索不可用就说不可用，禁止装作向量检索在工作；
3. **404 不可区分**：跨团队探测与真不存在必须是同一个页面；
4. **密钥一次性**：明文 key 只在铸造瞬间展示一次，任何页面不得提供「再看一次」；
5. **审计不可绕过**：payload 读取伴随审计；审计不可用则读取不可用（fail-closed）；
6. **actor 诚实**：来源事件没有 actor 就显示未知，不得脑补「系统」头像；
   `client_claimed` 的 actor 不出现在贡献者里；
7. **证据不可变**：证据链接一律指向 permalink（commit SHA 锚定），不是易变的
   branch 链接。
